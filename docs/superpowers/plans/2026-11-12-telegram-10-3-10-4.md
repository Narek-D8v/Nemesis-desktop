# Telegram 10.3/10.4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Использовать native drafts + Stop, rich-финалы, ephemeral-ответы
в группах и HTML-панель задачи в личке, сохранив текущее поведение при
любой ошибке Bot API.

**Architecture:** Новые возможности изолированы в трёх модулях
(`telegram_api.py`, `telegram_rich.py`, `telegram_widgets.py`) и
подключаются через один выключатель `telegram.advanced_ui`. Каждый новый
вызов имеет fallback на текущие `_Progress`/`start_message`; отмена агента
идёт через `threading.Event`, а история чинится синтетическими
tool-результатами.

**Tech Stack:** Python 3.13, python-telegram-bot 22.8 (Bot API 10.0),
PySide6, существующие `scripts/test_*.py`, `ruff`, `compileall`.

**Spec:** `docs/superpowers/specs/2026-11-12-telegram-10-3-10-4-design.md`

**Дата:** 2026-11-12  
**Объём:** B — native drafts + Stop, rich-финалы, ephemeral в группах,
HTML-панель задачи в личке. TON Wallet и shared widgets не входят.

## Global Constraints

- Python `>=3.13`; PTB `22.8`, библиотека сообщает Bot API `10.0`.
- Новые методы вызываются через raw `bot._post`; неизвестные typed-поля —
  из `Update.api_kwargs`.
- `telegram.advanced_ui` включён по умолчанию; `False` возвращает ровно
  текущее поведение.
- Любая ошибка нового API — graceful fallback, без падения задачи.
- Никаких живых запросов к Telegram, реального токена и Docker.
- TDD: сначала падающий тест, затем минимальная реализация.
- `venv\Scripts\python.exe -m ruff check .` и
  `venv\Scripts\python.exe -m compileall -q nemus scripts` — чистые.
- Тексты задач и токены не пишутся в логи.
- Сохранять модель доступа: `allowed_users`, `allow_groups`, private-only
  для виджетов и `widget_query`.

## Review Focus

Пять самых вероятных мест поломки; тест для каждого добавлен в задачу,
которая владеет кодом:

1. **Stop во время подтверждения инструмента.** Future должен стать
   `False`, клавиатура — исчезнуть, tool — получить отказ, задача —
   завершиться сразу, а не через `CONFIRM_TIMEOUT` (задача 6).
2. **Stop после assistant с `tool_calls`.** В истории не должно остаться
   `tool_calls` без `tool`-сообщений; partial-текст сохраняется
   (задача 5).
3. **Draft keepalive и fallback.** Долгий инструмент без событий: draft
   не истекает, Stop не исчезает; два сбоя keepalive дают ровно один
   `_Progress` (задача 4).
4. **Чужая/устаревшая панель.** Кнопка после рестарта, из чужого чата или
   под другим пользователем: ответ всегда, состояние не меняется,
   `/panel` создаёт новую (задачи 7–8).
5. **Rich-инъекция и порядок callback.** `<tg-button>`/`<script>` от
   модели экранируются; в группе ровно один `answerCallbackQuery` после
   успешного ephemeral, при ошибке — один alert (задачи 3 и 9).

Дополнительно: `advanced_ui=False` должен возвращать ровно текущее
поведение — без draft, rich, виджетов и ephemeral.

### `TelegramAdvancedAPI`

```python
class TelegramAdvancedAPI:
    def __init__(self, bot: Any) -> None: ...

    def available(self, endpoint: str) -> bool: ...

    async def send_message_draft(
        self, *, chat_id: int, draft_id: int, text: str
    ) -> bool: ...

    async def send_rich_message(
        self,
        *,
        chat_id: int,
        rich_message: dict[str, Any],
        reply_parameters: dict[str, Any] | None = None,
        reply_markup: dict[str, Any] | None = None,
    ) -> int | None: ...

    async def send_widget(
        self,
        *,
        chat_id: int,
        html: str,
        chat_data: str,
        caption: str,
        allow_queries: bool = True,
    ) -> int | None: ...

    async def edit_message_widget_data(
        self, *, chat_id: int, message_id: int, chat_data: str
    ) -> bool: ...

    async def answer_widget_query(
        self, *, widget_query_id: str, data: str
    ) -> bool: ...

    async def send_ephemeral(
        self,
        *,
        chat_id: int,
        callback_query_id: str,
        html: str,
        reply_markup: dict[str, Any] | None = None,
    ) -> int | None: ...
```

Адаптер всегда вызывает `bot._post(endpoint, payload)`. Точные payload:

```python
# sendMessageDraft
{"chat_id": chat_id, "draft_id": draft_id, "text": text,
 "can_stop": True, "keep_on_stop": True}

# sendRichMessage
{"chat_id": chat_id, "rich_message": rich_message,
 "reply_parameters": reply_parameters, "reply_markup": reply_markup}

# sendWidget
{"chat_id": chat_id, "html": html, "chat_data": chat_data,
 "caption": caption, "allow_queries": allow_queries}

# editMessageWidgetData
{"chat_id": chat_id, "message_id": message_id, "chat_data": chat_data}

# answerWidgetQuery
{"widget_query_id": widget_query_id, "data": data}

# ephemeral sendMessage
{"chat_id": chat_id, "text": html, "parse_mode": "HTML",
 "ephemeral_message_parameters": {"callback_query_id": callback_query_id},
 "reply_markup": reply_markup}
```

`None`-поля не отправляются. `sendMessageDraft` возвращает `bool`.
`sendRichMessage`, `sendWidget`, `sendMessage` возвращают `message_id` из
ответа или `None`. `answerWidgetQuery` и `editMessageWidgetData` возвращают
`True`; «message is not modified» считается успехом.

`BadRequest`/`NotFound` помечают endpoint недоступным только когда текст
ошибки содержит `method not found`, `not found`, `not supported`,
`unknown method` или `unsupported`; остальные `BadRequest` не кэшируются,
а пробрасываются вызывающему. Сетевые ошибки не кэшируются. Токен в логах
маскируется.

### Rich-модуль

```python
RICH_LIMIT = 32768

class RichTextTooLong(ValueError): ...

def prepare_rich_markdown(text: str) -> str: ...
def rich_button_rows(rows: list[list[tuple[str, str]]]) -> str: ...
def build_rich_markdown(
    text: str, rows: list[list[tuple[str, str]]] | None = None
) -> str: ...
```

`prepare_rich_markdown` вынимает fenced/inline-код в плейсхолдеры, экранирует
`<` в остальном тексте, возвращает код на место и проверяет `RICH_LIMIT`.
`build_rich_markdown` добавляет безопасные rich-кнопки и повторно проверяет
лимит уже с кнопками. Подписи кнопок экранируются; `data` обязан быть
1–64 байта UTF-8. Стиль: `primary` у первой кнопки, `link` у `ux:help`,
`secondary` у остальных.

### Draft-прогресс

```python
class _DraftProgress:
    def __init__(
        self, api: TelegramAdvancedAPI, bot: Any, chat_id: int
    ) -> None: ...

    draft_id: int
    async def start(self, text: str) -> None: ...
    async def note(self, text: str) -> None: ...
    async def tail(self, text: str, *, force: bool = False) -> None: ...
    async def close(self) -> None: ...
    async def fail(
        self, text: str, reply_markup: Any | None = None
    ) -> None: ...
```

Константы в `telegram_bot.py`: `DRAFT_KEEPALIVE = 10.0`,
`DRAFT_KEEPALIVE_FAILS = 2`. Первый вызов draft: `text=""`,
`draft_id = time.time_ns() & 0x7fffffff or 1`. Keepalive каждые 10 секунд
повторяет текущий рендер. Первый сбой обычного обновления — fallback на
`_Progress`; для keepalive fallback после двух сбоев подряд. Fallback
переигрывает base/notes/tail в `_Progress` без дублирования.

### Виджет-панель

```python
WIDGET_INTERVAL = 1.5
PANEL_DELAY = 1.5

def make_state(
    *, task_id: int, status: str, title: str, steps: list[str],
    start: float, end: float = 0.0, error: str = "", retry: bool = False,
) -> dict[str, Any]: ...

def truncate_state(state: dict[str, Any]) -> dict[str, Any]: ...
def state_json(state: dict[str, Any]) -> str: ...
def parse_widget_action(data: str) -> tuple[str, int | None]: ...

class WidgetPanel:
    message_id: int
    state: dict[str, Any]

    @classmethod
    async def create(
        cls, api: TelegramAdvancedAPI, *, chat_id: int,
        task_id: int, title: str,
    ) -> "WidgetPanel | None": ...

    async def update(
        self, api: TelegramAdvancedAPI, *, chat_id: int,
        force: bool = False, **changes: Any,
    ) -> None: ...

    async def close(
        self, api: TelegramAdvancedAPI, *, chat_id: int,
        status: str, error: str = "", retry: bool = False,

```

Ключи состояния: `v`, `id`, `s`, `t`, `steps`, `start`, `end`, `err`,
`retry`. `state_json` использует compact JSON и `ensure_ascii=False`;
результат всегда ≤1024 байта UTF-8. `WIDGET_HTML` — статическая строка без
пользовательских данных; состояние выводится только через `textContent`.
Кнопки отправляют `stop:<id>`, `retry:<id>`, `status`, `new`, `help`.

### Интеграция в `TelegramBot`

Новые поля:

```python
self._api: TelegramAdvancedAPI | None = None
self._draft_id: int | None = None
self._draft_chat_id: int | None = None
self._stop_event: threading.Event | None = None
self._current_task_id: int | None = None
self._current_task_chat: int | None = None
self._task_seq: dict[int, int] = {}
self._last_task_ids: dict[int, int] = {}
self._panels: dict[int, WidgetPanel] = {}
self._active_progress: Any | None = None
```

`_api` создаётся в `_thread_main` после `_build_application()`. В тестах
он подставляется явно.

Новые/изменённые методы:

```python
async def _send_final(
    self, chat_id: int, message_id: int | None, text: str,
    *, stopped: bool = False,
) -> None: ...

async def _ensure_panel(
    self, chat_id: int, task_id: int, title: str, chat_type: str | None
) -> None: ...

async def _finish_panel(
    self, chat_id: int, task_id: int, status: str,
    *, error: str = "", retry: bool = False,
) -> None: ...

def _request_stop(
    self, chat_id: int, *, draft_id: int | None = None,
    task_id: int | None = None,
) -> bool: ...

def _deny_pending_confirmations(self, chat_id: int) -> None: ...

async def _callback_message(
    self, query: Any, text: str, reply_markup: Any | None = None
) -> None: ...

def _short_status(self, chat_id: int) -> str: ...
def _short_help(self) -> str: ...
```

`_run_task_for` получает параметры `chat_type: str | None = None` и
`retry: bool = False`. Draft выбирается только при
`chat_type == "private"`, включённом `advanced_ui`, наличии `_api`,
`_api.available("sendMessageDraft")` и `retry is False`.
Rich-финал — только private + advanced + `_api`; иначе `start_message`.
Повтор после ошибки (`retry=True`) идёт через `_Progress`.

`_last_tasks` и `_last_task_ids` заполняются **внутри** `_task_lock`.
`_task_seq[chat_id]` увеличивается при старте задачи. Stop действует только
на текущую задачу; задача, ждущая lock, не отменяется.
