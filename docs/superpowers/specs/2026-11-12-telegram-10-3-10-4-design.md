# Telegram 10.3/10.4: нативный чат, rich-ответы и виджет-панель

**Дата:** 2026-11-12  
**Статус:** черновик, ждёт утверждения  
**Выбранный объём:** B — native chat + HTML-панель задачи. TON Wallet,
shared widgets и остальные второстепенные возможности 10.4 не входят.

## Зачем

Сейчас Telegram-бот Немуси показывает прогресс одним редактируемым
сообщением: «Думаю…», строки инструментов, хвост ответа. Это работает, но
выглядит как обычный чат-бот и не использует возможности Bot API 10.3/10.4:

- ответ нельзя стримить нативно и остановить кнопкой;
- финальный Markdown теряет заголовки, списки и таблицы: `to_html` делает
  заголовки жирными, а таблицы — моноширинным блоком;
- в группах ответы на кнопки видят все участники;
- нет живой панели с состоянием задачи и быстрыми действиями.

Цель — сделать общение с Немусей в Telegram заметно удобнее, не меняя
модель доступа, не ломая текущие сценарии и оставляя откат на старый
прогресс при любой ошибке API.

## Что уже есть

- `python-telegram-bot 22.8`, библиотека сообщает Bot API **10.0**.
- `Bot.send_message_draft(chat_id, draft_id, text, api_kwargs=...)` уже есть.
- Обёрток `sendRichMessage`, `sendRichMessageDraft`, `sendWidget`,
  `editMessageWidgetData`, `answerWidgetQuery` в PTB нет.
- `Update.de_json` сохраняет неизвестные top-level поля в `api_kwargs`;
  это проверено для `stopped_message_generation` и `widget_query`.
- `_Progress` редактирует одно сообщение; `start_message` отправляет
  Markdown→HTML чанками; `_on_callback` обслуживает `ux:*` и `tg:*`.
- `Agent.run` не умеет отменять генерацию; `/stop` сейчас останавливает
  всего бота, а не текущую задачу.
- Виджеты и drafts в production разрешены только в приватных чатах. В
  группах остаётся текущий прогресс и обычные сообщения.

## Цели

- В личке показывать нативный стрим через `sendMessageDraft` с кнопкой
  «Стоп» и сохранением частичного ответа.
- Отправлять финальный ответ rich-сообщением: заголовки, списки, таблицы,
  цитаты, код, формулы и rich-кнопки. HTML-блоки `<details>` и другие
  теги от модели не принимаются: санитайзер их экранирует.
- Показывать в личке живую HTML-панель задачи: статус, шаги инструментов,
  таймер, кнопки «Стоп / Статус / Новый / Повторить / Помощь».
- Отвечать на кнопки в группах ephemeral-сообщением: видит только
  нажавший.
- При любой ошибке нового API откатываться на текущее поведение, не
  теряя задачу и не ослабляя доступ.

## Не цели

- TON Wallet, платежи, подписи и `sendSharedWidget`.
- Виджеты и drafts в группах, inline-режим, бизнес-аккаунты, каналы.
- Замена GUI, перенос истории диалога или изменение агентской логики за
  пределами отмены текущей генерации.
- Собственный Markdown-парсер и собственный HTML-рендерер rich-сообщений:
  используем `InputRichMessage(markdown=...)` и санитайзер.

## Анти-цели

- Панель не должна дублировать весь GUI и превращать чат в дашборд.
- Нельзя отправлять в виджет токены, ключи, полный системный промпт или
  содержимое файлов.
- Нельзя принимать решение по `widget_query.data` без проверки панели,
  пользователя и версии задачи.
- Нельзя оставлять пользователя без ответа, если Telegram не поддерживает
  новинки: fallback обязателен.
- Нельзя ломать группы, где виджеты в production недоступны.

## Ограничения

- Работаем без живой проверки Telegram и Docker; проверка — тесты и
  `ruff`, `compileall`.
- PTB 22.8 знает только Bot API 10.0, поэтому новые методы вызываются
  через тонкий raw-адаптер поверх `Bot._post`.
- Draft живёт около 30 секунд; после финала обязательно отправить обычное
  или rich-сообщение.
- Rich-сообщение: до 32768 UTF-8 символов, 500 блоков, 16 уровней
  вложенности.
- Виджет: HTML 1–32768 байт, сжатый zlib ≤4096 байт; `chat_data` ≤1024
  байт; запрос ≤64 байт; ответ ≤1024 байт; ответ на `widget_query` — за
  15 секунд; лимит 5 запросов / 5 секунд на пользователя.
- `stopped_message_generation` и `widget_query` не имеют typed-полей в
  PTB 22.8; читаем их из `Update.api_kwargs` и считаем недоверенными.

## Контракт новых API

Источники: `core.telegram.org/bots/api` (`sendMessageDraft`,
`sendRichMessage`, `sendRichMessageDraft`, `sendWidget`,
`editMessageWidgetData`, `answerWidgetQuery`, `WidgetQuery`, `Update`) и
`core.telegram.org/bots/widgets`. Это единственный контракт, на который
опирается реализация: живой проверки Telegram в этой задаче нет, поэтому
все вызовы изолированы в адаптере и тестируются по документированным
payload'ам. Если сервер поведёт себя иначе, сработает fallback, а не
поломка задачи.

### Drafts и Stop

- `sendMessageDraft` работает только в приватном чате.
- `draft_id` — целое, не ноль; изменения с тем же `draft_id` анимируются.
- `text` — 0–4096 символов; пустая строка показывает нативный
  «Thinking…».
- `can_stop=True` показывает кнопку остановки. Нажатие приходит как
  top-level поле Update **`stopped_message_generation`** (не
  `message_generation_stopped`), объект `MessageGenerationStopped`:
  `chat`, опциональный `message_thread_id`, `draft_id`.
- `keep_on_stop=True` оставляет черновик в чате после нажатия, но он всё
  равно исчезает через короткое время или после сообщения бота. Поэтому
  частичный текст надо отправить отдельным сообщением.
- Draft — временный 30-секундный preview. Нужен keepalive, иначе при
  долгом инструменте или подтверждении черновик и кнопка Stop исчезнут.

### Rich-сообщения и кнопки

- `sendRichMessage` принимает `rich_message: InputRichMessage`; используем
  `{ "markdown": text }`.
- Лимиты: 32768 UTF-8 символов, 500 блоков, 16 уровней вложенности.
- Rich Markdown поддерживает заголовки, списки, таблицы, цитаты, код,
  формулы, сноски и HTML-теги. Мы **не** пропускаем HTML-теги модели:
  санитайзер экранирует `<`, поэтому `<details>`, `<script>`, `<img>` и
  `<tg-button>` из ответа модели не исполняются.
- Кнопки задаются только нашей строкой:
  `<tg-button-row align="center"><tg-button type="callback_data"
  data="ux:new" style="primary">Новый диалог</tg-button></tg-button-row>`.
  `callback_data` — 1–64 байта; `style` — `danger`, `success`, `primary`
  или `link`; `link` разрешён только для callback-кнопок.
- `reply_parameters` принимает `message_id`; `allow_sending_without_reply`
  позволяет не падать, если исходное сообщение удалено.

### Виджеты

- `sendWidget` в production работает только в приватных чатах.
- `html` — 1–32768 байт и ≤4096 байт после `zlib.compress(..., 9)`.
- `chat_data` и `public_data` — 0–1024 байт; `caption` — 0–1024 символа.
- `allow_queries=True` разрешает `TelegramWidget.request`.
- `is_shared` не используем: нужен статический виджет на одно сообщение,
  без `sendSharedWidget` и `shared_widget_query`.
- `sendWidget` возвращает `Message`; `message_id` берём из ответа.
- `editMessageWidgetData` принимает `chat_id` + `message_id` и
  `chat_data`/`public_data`; «message is not modified» считается успехом.
- `WidgetQuery` (оригинал, не forward) содержит `id`, `from`, `chat`,
  `message_id`, `chat_instance`, `type`, `data`, опциональный `widget_id`.
  Состояния виджета в запросе нет: авторитетное состояние храним у себя по
  `chat_id`/`message_id`.
- `TelegramWidget.request(data)` принимает 1–64 байта, возвращает промис
  `{ result: string | null }`; ошибки — `NOT_ALLOWED`, `BUSY`,
  `RATE_LIMITED`, `TIMEOUT`, `FAILED`, `INVALID_ANSWER`.
- `answerWidgetQuery(widget_query_id, data)` обязателен в течение 15 секунд.
  `data` (0–1024 байта) видит **только** виджет, который спросил; это не
  toast, не alert и не сообщение в чат. Виджет сам рисует `result`.
- Смена состояния — отдельный `editMessageWidgetData`; событие
  `chatDataChanged` приходит в виджет, после чего он перерисовывается из
  `TelegramWidget.chatData`.
- Один пользователь — не более 5 запросов за 5 секунд; лимит общий для
  всех виджетов бота.

### Ephemeral

- `sendMessage` и `sendRichMessage` принимают
  `ephemeral_message_parameters: { callback_query_id }`; при отсутствии
  `receiver_user_id` сообщение видит только нажавший.
- `callback_query_id` не заменяет `answerCallbackQuery`: Telegram требует
  отдельно ответить на callback query. Поэтому helper сначала отправляет
  ephemeral, затем при успехе вызывает `query.answer()`; ошибка ephemeral
  откатывается на `query.answer(..., show_alert=True)`. Callback остаётся
  acknowledged, а двойного ответа нет.

## Подходы

### A. Native chat

Drafts, Stop, rich-финалы, rich-кнопки и ephemeral в группах. Без виджетов.
Меньше кода и риска, но не использует самую интересную часть 10.4 —
живую панель.

### B. Native chat + интерактивная панель (выбран)

Всё из A плюс HTML-панель задачи в личке: `sendWidget`,
`editMessageWidgetData`, `answerWidgetQuery`, состояние панели, действия
«Стоп / Статус / Новый / Повторить / Помощь». Панель переиспользуется для
следующих задач, чтобы не засорять чат. В группах — fallback на текущий
прогресс. Это лучший баланс пользы, риска и полноты API.

### C. Full showcase

B плюс TON Wallet, shared widgets и все мелкие возможности. Максимальный
охват, но появляется платёжный сценарий, которого у Немуси нет; больше
сырых вызовов и security-риска. Отложено до отдельного запроса.

## Пользовательские сценарии

### 1. Задача в личке

1. Пользователь отправляет текст.
2. Бот сразу показывает нативный черновик «Думаю…» с кнопкой «Стоп».
3. Если задача идёт дольше 1.5 секунды, появляется панель:

   ```text
   Немуся · работает 00:04
   «найди отчёт за март и пришли»
   🔧 read_file   🔧 run_shell
   [ Стоп ] [ Статус ] [ Новый ]
   ```

4. В черновике появляется хвост ответа; панель обновляет шаги и таймер.
5. Финал уходит rich-сообщением:

   ```text
   # Отчёт за март
   Нашла 3 файла. Главный — «Март 2026.xlsx».

   | Файл | Дата |
   |---|---|
   | Март 2026.xlsx | 12.03 |

   [ Повторить ] [ Новый диалог ] [ Помощь ]
   ```

6. Панель переходит в «Готово», остаётся в чате как компактный чек и
   переиспользуется для следующей задачи.

### 2. Остановка

- Кнопка «Стоп» есть в нативном черновике и в панели.
- Бот получает `stopped_message_generation` (для draft) или
  `widget_query` с `stop:<id>` (для панели), ставит событие отмены.
- Агент завершает текущий шаг/поток и отдаёт `stopped`.
- Бот отправляет частичный ответ с пометкой «Остановлено» или «Остановила
  задачу», если текста ещё нет. Ошибкой это не считается.
- `/stop` по-прежнему останавливает самого бота; это разные действия.

### 3. Ошибка

- Если rich-сообщение не принято, тот же текст уходит старым
  `start_message` с HTML-чанками и обычной inline-клавиатурой.
- Если виджет не отправился, задача продолжается через `_Progress`; панель
  просто не появляется.
- Если draft не поддерживается, первый же вызов падает, и прогресс
  переключается на `_Progress`.
- Пользователь всегда видит причину ошибки и кнопки «Повторить / Новый /
  Помощь», как сейчас.

### 4. Группа

- Прогресс — текущий `_Progress`.
- Информационные ответы на кнопки (`Статус`, `Помощь`, `Примеры`, `Скиллы`,
  подтверждение нового диалога) уходят ephemeral-сообщением только
  нажавшему.
- Если ephemeral не поддерживается, бот отвечает `query.answer(...,
  show_alert=True)`; публичного спама нет.
- Виджеты и drafts в группах не используются.

### 5. `/panel`

- В личке отправляет или переиспользует панель в состоянии «свободна».
- В группе или при выключенном `advanced_ui` отвечает обычной справкой и
  меню.
- Панель — не замена `/status` и `/help`, а быстрый доступ к тем же
  действиям.

## Техническая архитектура

### Новые модули

- `nemus/core/telegram_api.py` — тонкий адаптер новых методов Bot API:
  `send_message_draft`, `send_rich_message`, `send_widget`,
  `edit_message_widget_data`, `answer_widget_query`, `send_ephemeral`.
  Хранит флаги доступности методов, не даёт повторять заведомо
  неподдерживаемый вызов, маскирует токен в ошибках.
- `nemus/core/telegram_rich.py` — чистые функции:
  `prepare_rich_markdown`, `rich_button_rows`, проверка лимитов. Без
  сетевых вызовов, легко тестируется.
- `nemus/core/telegram_widgets.py` — статический HTML панели, сериализация
  состояния, `WidgetPanel` (send/update/close), разбор действий
  `widget_query`.
- `nemus/core/telegram_bot.py` — оркестрация: выбор прогресса, отмена,
  финалы, панель, ephemeral, регистрация raw-обработчиков.
- `nemus/core/agent.py` — опциональная отмена `Agent.run(..., stop=...)` и
  событие `stopped`.
- `nemus/config.py`, GUI и `config/config.example.yaml` — один выключатель
  `telegram.advanced_ui`.

### Raw-адаптер

`TelegramAdvancedAPI` получает PTB `Bot` и вызывает `bot._post(endpoint,
payload)`. Вложенные объекты передаются обычными `dict`/`list`:

```python
await api.send_rich_message(
    chat_id=chat_id,
    rich_message={"markdown": text},
    reply_parameters={"message_id": message_id, "allow_sending_without_reply": True},
)

await api.send_widget(
    chat_id=chat_id,
    html=WIDGET_HTML,
    chat_data=state_json,
    caption="Панель Немуси",
    allow_queries=True,
)
```

Правила адаптера:

- `None` не отправляем; пустые обязательные поля проверяем до вызова.
- `BadRequest`/`NotFound`/«method not found»/«not supported» помечают метод
  как недоступный до перезапуска; сетевые и временные ошибки не кэшируем.
- `sendWidget`, `sendRichMessage`, `sendMessage` возвращают `Message` dict;
  берём из него `message_id`; `answerWidgetQuery` и
  `editMessageWidgetData` возвращают `True`.
- Все вызовы логируются без текста пользователя и без токена.

### Draft-прогресс

Добавляется `_DraftProgress` с тем же интерфейсом, что у `_Progress`:
`start/note/tail/close/fail`.

- `start`: `chat_id`, `draft_id = time.time_ns() & 0x7fffffff or 1`,
  `text=""` (нативный «Thinking…»),
  `api_kwargs={"can_stop": True, "keep_on_stop": True}`, только private.
- `note/tail`: рендерят base + последние заметки + хвост, режут до 3900
  символов, отправляют не чаще `PROGRESS_INTERVAL` (1.5 с); при reset
  очищают хвост.
- `keepalive`: каждые 10 секунд повторяет текущий рендер, даже если
  событий нет. Это удерживает 30-секундный draft и кнопку «Стоп» во время
  долгого инструмента или ожидания подтверждения.
- `close`: останавливает keepalive; для draft — no-op, draft исчезнет
  после финального сообщения.
- `fail`: останавливает keepalive и отправляет обычное сообщение об
  ошибке; draft исчезает.
- Первый же сбой draft (группа, старый сервер, нет метода) переключает
  объект на внутренний `_Progress`; дальше поведение полностью старое.
  Для keepalive допускаем два подряд сбоя, затем тоже fallback: если
  черновик всё-таки истёк, у пользователя снова есть обычный прогресс.
- `_run_task_for` выбирает draft только если чат private, включён
  `advanced_ui`, у бота есть `send_message_draft`, и это не повтор после
  ошибки.

### Отмена задачи

- `AgentEvent.kind` расширяется значением `"stopped"`.
- `Agent.run(user_text, images=None, stop: threading.Event | None = None)`.
- `_stream_response(tools, stop)` накапливает куски текущего ответа; при
  установленном событии поднимает внутреннее `GenerationStopped(partial)`,
  которое `run` превращает в `AgentEvent(kind="stopped")` и завершает
  работу. Перед этим `run` вызывает `_finalize_stopped(partial)` из
  раздела про отмену: сохраняет частичный ответ и закрывает висящие
  tool-calls.
- Проверки отмены: перед каждым шагом, после каждого стрим-куска и перед
  каждым вызовом инструмента. Долгий инструмент не прерывается посередине;
  отмена сработает после его возврата.
- `TelegramBot` хранит `_stop_event`, `_draft_id`, `_draft_chat_id` текущей
  задачи. `_run_task_for` создаёт событие и передаёт его в `agent.run`.
- `stopped_message_generation` приходит как неизвестное поле Update;
  `TypeHandler(Update, ...)` читает `update.api_kwargs`, проверяет
  `chat.id` и `draft_id`, ставит событие только для совпадающей задачи.
- `widget_query` с `stop:<task_id>` делает то же самое после проверки
  панели и пользователя.
- Ожидание подтверждения инструмента (`_confirm`/`_ask_confirm`) не
  должно висеть до `CONFIRM_TIMEOUT`. `_confirm` опрашивает
  `_stop_event` каждые 0.25 с; при остановке future подтверждения
  разрешается как `False`, клавиатура снимается, а tool получает отказ.
  Тот же путь вызывает обработчик Stop, чтобы не ждать агентского треда.
- Stop действует только на текущую задачу. Сообщение, которое ждёт
  `_task_lock`, не отменяется: оно стартует после завершения текущей
  задачи. Это сохраняет текущую очередь.
- `_last_tasks[chat_id]` заполняется **внутри** `_task_lock`, а не в
  начале `_run_task_for`. Иначе постановка в очередь перезаписывала бы
  задачу, к которой относится кнопка «Повторить».
- При остановке `Agent` обязан оставить историю валидной:
  - если частичный текст уже есть, он сохраняется как assistant-сообщение
    (без `tool_calls`), чтобы следующий ход видел, что успело сказаться;
  - если assistant-сообщение с `tool_calls` уже сохранено, но результаты
    инструментов не пришли, для каждого недостающего `tool_call_id`
    добавляется синтетический `tool`-результат «Выполнение остановлено
    пользователем» и сохраняется в память;
  - `pair_tool_messages` при загрузке остаётся страховкой, но live-историю
    чиним сразу, иначе следующий запрос может получить отказ провайдера.
- Если пришёл `stopped`, `final_text` не считается ошибкой: бот
  отправляет частичный текст с пометкой «Остановлено» или короткое
  «Остановила задачу». Реакция и первая подсказка не ставятся.

### Rich-финалы

- Финальный текст отправляется `sendRichMessage` с
  `rich_message={"markdown": safe_text}`.
- Перед отправкой `prepare_rich_markdown`:
  - вынимает fenced- и inline-код в плейсхолдеры;
  - экранирует `<` в остальном тексте, чтобы модель не могла внедрить
    `<tg-button>`, `<script>` или другие HTML-теги;
  - возвращает код на место;
  - при необходимости добавляет нашу безопасную строку
    `<tg-button-row>` с кнопками;
  - проверяет 32768 символов; если больше — сигнал на fallback.
- Rich-кнопки используют те же callback-данные, что текущие `ux:*`:
  `Повторить`, `Новый диалог`, `Помощь`. Точный вид:
  `<tg-button-row align="center"><tg-button type="callback_data"
  data="ux:new" style="primary">Новый диалог</tg-button>...</tg-button-row>`.
  Стили: `primary` для основного действия, `link` для помощи.
- Сворачиваемые `<details>` и прочий HTML от модели не поддерживаем:
  это цена за то, что модель не может внедрить собственную кнопку или
  тег. При необходимости такие блоки будут добавляться только нашей
  разметкой, а не текстом ответа.
- Если rich-вызов не удался или текст слишком длинный, вызывается текущий
  `start_message` с `_keyboard(rows)`; клавиатура ставится на последний
  чанк, как сейчас.
- Ошибки по-прежнему отправляются через `progress.fail`, чтобы не менять
  привычное поведение восстановления.

### Виджет-панель

`WidgetPanel` — один объект на чат, переиспользует сообщение между
задачами.

Состояние (компактные ключи, JSON, ≤1024 байт):

```json
{
  "v": 1,
  "id": 7,
  "s": "working",
  "t": "найди отчёт за март",
  "steps": ["read_file", "run_shell"],
  "start": 1760000000,
  "end": 0,
  "err": "",
  "retry": true
}
```

- `id` — номер задачи в этом чате; кнопки отправляют `stop:7`, `retry:7`
  и т.п. Счётчик живёт в памяти процесса, начинается с 1; `idle` — 0.
  Это не глобальный идентификатор и не обязательство пережить рестарт.
- `s`: `idle`, `working`, `done`, `error`, `stopped`, `stopping`.
- `t` — первые ~80 символов задачи, `steps` — до 6 имён инструментов,
  `err` — короткая причина.
- `truncate_state` убирает лишние шаги/ошибку, пока JSON не влезет в 1024
  байта; кириллица считается в UTF-8. Усечение — часть контракта, а не
  ошибка: панель никогда не должна отвергаться сервером из-за размера.

HTML панели — статическая строка без пользовательских данных:

- шапка «Немуся» и статус;
- preview задачи через `textContent` (никакого `innerHTML` из состояния);
- чипы шагов;
- таймер на `setInterval` от `start`/`end`;
- кнопки с `TelegramWidget.request(...)`, обработка `WidgetRequestError`;
- `TelegramWidget.onEvent('chatDataChanged', render)`;
- тема через CSS-переменные, без внешних ресурсов и `fetch`;
- HTML укладывается в 32 КБ и в 4 КБ после `zlib.compress(..., 9)`.

Отправка и обновление:

- `sendWidget` в private с `allow_queries=True`, `caption="Панель
  Немуси"`, `chat_data=state`; `is_shared` не передаём.
- `editMessageWidgetData` не чаще 1.5 с; при «message is not modified»
  считаем успехом; при исчезнувшем сообщении панель помечается сломанной.
  Если метод вообще не поддерживается, виджеты отключаются до
  перезапуска, а задача продолжается на `_Progress`.
- Панель создаётся через 1.5 с после старта задачи, если задача ещё идёт;
  короткие ответы панель не создают. Если панель уже есть — она
  переиспользуется и переводится в `working` без нового сообщения.
- Сломанная панель выбрасывается из `_panels`; следующая задача создаёт
  новую. Старое сообщение не удаляем: его кнопки всё равно ответят
  «панель устарела».
- `_panels` и счётчик `task_id` — in-memory. После рестарта бота старые
  виджеты остаются в чате, но их запросы не находят панель; обработчик
  отвечает «Панель устарела, откройте /panel». `/panel` создаёт новую
  панель. Это осознанно: восстанавливать `message_id` старого виджета
  без живого Telegram нельзя.
- При финале/ошибке/остановке состояние обновляется. `retry` включается,
  только если `_last_task_ids[chat_id] == task_id` панели и
  `_last_tasks[chat_id]` не перезаписан следующей задачей. `_last_tasks`
  и `_last_task_ids` заполняются внутри `_task_lock`.

Действия `widget_query` (все проверяются по панели и `task_id`):

| data | Действие |
|---|---|
| `stop:<id>` | проверить `id`, поставить `_stop_event`, ответить «Останавливаю…», состояние `stopping` |
| `status` | ответить коротким статусом из `_status_text` (≤1024 байт), без изменения состояния |
| `new` | если задача идёт — отказ; иначе очистить сессию, `_last_tasks`/`_last_task_ids`, состояние `idle` |
| `retry:<id>` | проверить `id`, если задача идёт — отказ; иначе ответить и запустить `_run_task_for` в `asyncio.create_task` |
| `help` | ответить короткой справкой (≤1024 байт); полная — через `/help` |
| иное | ответить «Неизвестное действие» |

- Обработчик читает `widget_query` из `Update.api_kwargs`, проверяет
  `type` (только `data`; wallet/иные не обслуживаем), `from.id`, private
  chat, `chat_id`/`message_id` и `task_id` панели.
- Ответ на `widget_query` отправляется всегда и сразу, в пределах 15 с.
  `answerWidgetQuery` не меняет состояние и не показывает toast: текст
  ответа рисует сам виджет в своей строке статуса. Поэтому `status` и
  `help` — короткие; длинный статус доступен командой `/status`.
- `from.id` обязан быть в `allowed_users`; чат — private; панель должна
  существовать и совпадать по `chat_id`/`message_id`.
- `data` — недоверенная строка: только точный список действий, без
  `eval`, без путей и без секретов.
- `/panel` вызывает тот же `WidgetPanel`; при ошибке — обычная справка с
  меню. `/panel` не переиспользует чужую/устаревшую панель по догадке.

### Ephemeral в группах

Добавляется helper `_callback_message(query, text, reply_markup=None)`:

- private → `query.answer()` (ровно один раз) и текущий `start_message`;
- group/supergroup и `advanced_ui` → сначала raw `sendMessage` с
  `ephemeral_message_parameters={"callback_query_id": query.id}`,
  `parse_mode="HTML"` и текстом после `to_html`; при успехе затем
  `query.answer()` (Telegram требует ответить на callback отдельно); при
  ошибке — `query.answer(text[:200], show_alert=True)`, без публичного
  сообщения;
- `advanced_ui=False` → `query.answer()` и текущее публичное поведение.

Вызывающие ветки `_on_ux_callback` не должны отвечать на callback до
helper, иначе получится двойной `answerCallbackQuery`. Если ветка уже
ответила (например, из-за своей логики), она не использует helper.

Заменяются только информационные ответы `_on_ux_callback` (`help`,
`examples`, `skills`, `status`, `new`). Подтверждения опасных инструментов
и действия с вложениями остаются как есть: они уже привязаны к чату,
пользователю и сообщению.

### Конфигурация

В `TelegramConfig` добавляется:

```python
#: drafts, rich-сообщения, виджеты и ephemeral-ответы (Bot API 10.3+)
advanced_ui: bool = True
```

- GUI: чекбокс в Telegram-вкладке «Живой ответ и панель задач» с
  подсказкой; сохранение/загрузка через `dialogs.py`.
- i18n: `tg.advanced_ui` и `tg.advanced_ui_tip` для ru/en.
- `config/config.example.yaml`: поле и комментарий.
- По умолчанию включено; выключение возвращает ровно текущее поведение.

### Безопасность

- Доступ проверяется до любых новых вызовов: `allowed_users`, группы —
  по `allow_groups`; для `widget_query` — `from.id` и private chat.
- Панель привязана к `chat_id` + `message_id` + `task_id`; чужая или
  устаревшая кнопка получает отказ.
- В `chat_data` нет токенов, ключей, полного промпта и содержимого файлов;
  только короткий preview, имена инструментов и статус.
- HTML виджета статический; состояние вставляется через `textContent`.
- Rich Markdown санитайзер не даёт модели добавлять HTML-кнопки и теги;
  наши кнопки добавляются только после очистки.
- Ephemeral-ответы отправляются только авторизованному пользователю;
  fallback alert не раскрывает данные другим.
- Ошибки логируются с маскировкой токена; тексты задач в логи не пишем.

## Матрица fallback

| Что | Основной путь | Если не поддерживается |
|---|---|---|
| Прогресс | `sendMessageDraft` в private | `_Progress` в сообщении |
| Финальный ответ | `sendRichMessage` | `start_message` + HTML-чанки |
| Rich-кнопки | `<tg-button-row>` | обычная inline-клавиатура |
| Панель | `sendWidget` / `editMessageWidgetData` | `_Progress`, без панели |
| Действия панели | `answerWidgetQuery` | ответ не нужен, панель не создаётся |
| Групповые ответы | ephemeral `sendMessage` | `query.answer(show_alert=True)` |
| Stop | draft update / widget query | старый прогресс, `/stop` как раньше |

## Решения, которые принимаю я

- Панель автоматическая для задач дольше 1.5 с; иначе не создаётся.
- Одна панель на чат, переиспользуется между задачами.
- Финальный ответ — rich для всех успешных ответов; ошибки остаются на
  текущем `progress.fail`.
- Rich-кнопки только в финале; подтверждения инструментов остаются на
  обычных inline-кнопках.
- Ephemeral — только для информационных `ux:*` ответов в группах, не для
  подтверждений.
- `advanced_ui` по умолчанию включён; выключение — полный откат.
- HTML-теги модели не пропускаем; `<details>` и другие rich-HTML-блоки
  остаются за рамками, пока не появится безопасная разметка.
- Панель живёт в памяти; после рестарта старые виджеты инертны, `/panel`
  создаёт новую. Это лучше, чем пытаться угадать `message_id`.
- Остановка не оставляет «грязную» историю: частичный assistant-текст и
  синтетические tool-результаты сохраняются сразу.

## Открытые вопросы

Нет вопросов, блокирующих план. Известное ограничение проверки: живой
Telegram в этой задаче не запускается, поэтому контракт новых методов
проверяется по документации и golden-payload-тестам, а не на реальном
ботовом API. Если живая проверка покажет расхождение, адаптер помечает
метод недоступным и включает fallback без изменения кода сценариев. Это
не блокирует план, но должно быть первым, что проверяется при следующем
живом запуске.
